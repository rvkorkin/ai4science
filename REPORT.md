## 3. Что именно проверяется

### A. Property-based causality (`test_causality.py`, Hypothesis)

Инвариант: выход предобработки в момент времени `i` зависит **только** от входа до
реального времени `i·R` (R — фактор децимации). Проверка — рандомизированным
возмущением будущего: для случайных `x`, `R`, формы и `seed` возмущаем вход начиная
с индекса `k` и требуем побитового (с точностью `atol`) совпадения тех выходных
строк, которые физически не могли «увидеть» `k`.

| Функция (`src/preprocess.py`) | Свойство |
|---|---|
| `decimate_causal` | каузальный LP+децимация: будущее не влияет на прошлые выходы; `M = N//R`; возмущение `x[0]` ОБЯЗАНО менять `y[0]` (тест не вырожден) |
| `strain_rate_causal` | backward-diff + EWMA: `y[t]` зависит только от `strain[:t+1]`, `y[0]=0` |
| `strain_rate_from_raw` | полная цепочка (пространств. сглажка → sr → децимация) каузальна по времени |

### A. Leakage в split (`test_leakage.py`)

Инварианты схемы leave-one-GROUP-out на `split.json` + `field_strongest_hits.json`:
- `train ∩ val = ∅` (на уровне стемов), отсутствие дублей внутри сплита;
- каждый стем сплита имеет запись в лейблах;
- для hit-файлов `0 ≤ tpk < T`;
- отчётная (мягкая) метрика пересечения treatment-well групп train/val.

### B. Валидатор данных (`validate_data.py`, `test_validator.py`)

Для каждого npz: наличие ключей (`strain, depth, strain_rate, dt_sec`), согласованность
форм (`strain (T,D)`, `strain_rate==strain`, `depth (D,)`, `dist_profile_m (D,)`),
конечность значений (NaN/inf → ошибка), `dt_sec>0`, монотонность и шаг глубины,
кросс-проверка лейблов (`T/D`, `tpk` в диапазоне). Юнит-тесты валидатора — на
синтетических «хороших» и битых записях.

## 4. План численного эксперимента

1. Разрешить `FIELD_DATA_DIR` из `.env` форка проекта.
2. Загрузить канонический лейбл-файл `core/field_strongest_hits.json`.
3. Прогнать валидатор по всем `*.npz` → `validation_report.csv` (построчно) +
   `validation_summary.json` (агрегат).
4. Провести аудит `split.json`: дизъюнктность, покрытие лейблами, `tpk`, пересечение
   well-групп.
5. Записать объединённый отчёт `experiment_summary.json`.

Критерий «hard-fail» эксперимента: есть хоть одна ошибка валидации, либо пересечение
стемов train/val, либо `tpk` вне диапазона.

## 6. Находки и ограничения

- **`label_T_mismatch` (9 записей CrownQuest).** В лейблах `T` хранится в сырых
  10-с сэмплах (напр. 3021), а enriched-npz уже децимирован до минут (101). Это
  реальная рассинхронизация метаданных: поле `T` лейбла для CrownQuest нельзя
  использовать как длину минутного ряда. Валидатор это ловит; на `tpk`-проверку не
  влияет (эти записи no-hit). Инструмент `fix_labels.py` нормализует их к минутной сетке.
- **`strain_rate_extreme` (327).** Абсолютные значения strain_rate различаются на
  порядки между датасетами (CrownQuest ~1e-6 против сырых счётчиков HFTS2/FORGE).
  Это не ошибка, а индикатор разнородных единиц/масштабов — аргумент за
  доменную нормализацию перед обучением.
- **`dz_out_of_range` (48).** Часть записей с шагом глубины вне [0.3, 6] м
  (разные интеррогаторы/датасеты). Для них пространственная сглажка в метрах должна
  задаваться аккуратно.
- **Пересечение well-групп train/val = 20.** Это ожидаемо: группа по постановке —
  treatment event (стадия), а не скважина, поэтому стадии одной скважины
  легитимно попадают в разные части. Метрика отчётная, не hard-fail; но это та самая
  зона, где стоит перейти к strict leave-one-WELL-out, если потребуется ещё более
  честная оценка.
- **Границы верификатора.** Property-тесты покрывают `preprocess.py` (чистые функции);
  причинность GRU/warmup-нормализации в `nn_pipeline`/`nn_seq_pipeline` здесь не
  тестируется (следующий шаг). Валидатор проверяет схему и физику, но не
  корректность самих лейблов хита — этим занимается расширение §8.

## 8. Неопределённость разметки → soft-labels → обучение (расширение)

Разметка хита шумная и по **наличию**, и по **времени/глубине**. Вместо точечной
метки оцениваем её как распределение: несколько независимых model-free оценщиков
(ручная метка, пик дифф-активности, коллапс клина по strain_rate — Леггетт, апекс
клина по strain) дают (t, depth); их **робастный разброс (медиана + MAD, |z|>2
отбрасывается)** = измеренный шум метки.

**Приоритет — время.** `t_target` = робастная медиана {manual, act, wedge_sr}
(физика клина в составе, но защищена от выбросов); `sigma_t` → ширина per-file
джиттера tpk (кап 15 мин); `w_time = 1/(1+sigma_t/20)` → вес временной головы.
Глубина вторична (`w_depth` от `sigma_d`).

Код: `consensus_uncertainty.py` (на 4 размеченных вручную кандидатах),
`gen_soft_labels.py` (пакетно по всем **135** hit-файлам train/val-сплита →
`results/soft_labels_full.csv`). Проводка — опт-ин в `core/nn_seq_pipeline.py`
проекта через `NN_SOFT_LABELS` (soft-labels только на train; val держит фиксированную
ручную метку, чтобы прогоны сравнивались). NLL-голова `(mu, log_sigma)` уже была.

**Эксперимент (GPU RTX 4000 Ada, 25 эпох, seed 0, 430 train / 40 val):**
baseline (ручные метки) vs soft (консенсус-таргеты + per-file веса/джиттер).

Честная оценка времени — на val hit-файлах (n=15), ошибка **near-field**
(истинное L_min ≤ 30 мин, где ETA и важна); арбитр — и ручная метка, и консенсус:

| метрика | baseline | soft |
|---|---|---|
| MAE прихода vs manual, мин | 21.8 | **21.0** |
| median vs manual | 20.6 | **19.4** |
| MAE vs consensus | 17.6 | **17.0** |
| median vs consensus | 18.9 | **12.2** |

Детекция, per-file (агрегат по max `nn_hit_p`, операционная точка по FAR≤0.10):

| метрика (val: 15 hit / 25 no-hit) | baseline | soft |
|---|---|---|
| AUC (per file) | 0.881 | **0.915** |
| recall @FAR≤0.10 | 0.000 | **0.733** |
| precision @FAR≤0.10 | — | 0.846 |

Итог: soft-labels улучшают near-field точность прихода и **резко** — детекцию:
baseline переобучился так, что при FAR≤0.10 recall падает в 0 (порог упирается в 1.0),
а soft при FAR 0.08 ловит 11/15 (recall 0.73, precision 0.85). Важная оговорка:
per-epoch val-L против ручных меток для soft выглядит хуже (0.924 → 1.120) — это
**смещённый арбитр** (soft обучался на клин-таргетах, намеренно расходящихся с
onset-смещённой ручной меткой); near-field метрика это снимает. Ограничения: 1 seed,
маленький val (15 hit). Сплит `split.json` — не строго leave-pair-out (пересечение
well-групп 20, см. §6), поэтому абсолютные AUC оптимистичны относительно честных
pairloo-OOF чисел проекта (`deploy/RUNS.md`: config C AUC 0.960 OOF).

Артефакты: `results/soft_labels_full.csv`, `results/consensus_uncertainty.csv`,
`results/ab_time_eval.json`, `results/stg28_wedge.png`.
