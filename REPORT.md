# ДЗ 3. Инструменты и масштаб --- отчёт

Репозиторий: `https://github.com/rvkorkin/ai4science/tree/hw3`, метка `hw3`.
Проект: LF-DAS frac-hit prediction (статья, ветка `article`).

## 1. Потребность и инструмент

**Потребность проекта.** В разделах статьи про результаты модель пишет
числа «из головы» (время прихода frac-hit в минутах), и эти числа
расходятся с нашим проверенным кодом. Нужен инструмент, который для
конкретной записи LF-DAS даст то число, которое получает код проекта.

**Инструмент.** `frac_hit_verify` (файл `mcp/frac_hit_mcp.py`,
MCP-сервер `frac-hit`). По пути к `.npz` возвращает JSON-вердикт: валиден
ли файл по схеме и физическим инвариантам, и --- если валиден --- оценку
времени прихода frac-hit в минутах по кинематике сходящегося клина (код
переиспользуется из ДЗ-2: `src/wedge_near.py`, `verify/validate_data.py`).

Сигнатура и строка документации (дословно, `mcp/frac_hit_mcp.py`):

```python
@mcp.tool()
def frac_hit_verify(npz_path: str, max_errors: int = 10) -> str:
    """Проверить запись LF-DAS и оценить время прихода frac-hit.

    Вызывать, когда модель пишет про результат на конкретной записи LF-DAS и
    должна сверить число минут до прихода с проверенным кодом проекта, а не
    со своей памятью. Также вызывать, когда нужно убедиться в валидности
    файла `.npz` (формы, конечность значений, монотонность глубины, dt>0).
    ...
    """
```

Проверка без агента:

```
$ python mcp/frac_hit_mcp.py --selftest
frac_hit_verify: проверки пройдены; hit_time_min=92.11 (эталон ~90),
errors=['dt_sec_invalid:0.0']
```

Код инструмента `[порождено]` (Cursor, Claude Opus 4.8) поверх
переиспользуемых модулей `src/wedge_near.py` и `verify/validate_data.py`,
проверено `python mcp/frac_hit_mcp.py --selftest` (код 0) и реальным
запуском из сценария ниже.

## 2. Вызов по описанию

Полный фрагмент сеанса --- `evidence/session_tool_call.md`. Главное:

Запрос пользователя (без имени инструмента):

> Мне нужно для раздела «Результаты» вставить одну строку вида «инструмент
> оценил время прихода frac-hit на записи такой-то в X мин». Прежде чем я
> поверю числу из своей головы, проверь файл и дай мне то число, которое
> получает наш проверенный код проекта.

Строка вызова из сеанса и ответ:

```
▸ frac_hit_verify frac-hit
{"file": "rec_hit.npz", "valid": true, "stats": {"T": 120, "D": 40,
 "dt_sec": 60.0}, "hit": {"estimated": true, "hit_time_min": 92.11,
 "closest_approach_idx": 90, "n_converging_steps": 37}}
```

**Что пришлось менять в docstring.** Первая версия описывала механику
инструмента («валидирует схему и считает кинематику клина...»). Модель
его не вызывала и писала число по памяти. Помогла правка первого абзаца
docstring на прямое «Вызывать, когда модель пишет про результат на
конкретной записи LF-DAS...»: после этого инструмент вызывается сразу.

## 3. Сценарий

Задача (`scenario/task.md`): написать 3--5 предложений про вердикт
инструмента на `scenario/fixtures/rec_hit.npz`. Должны совпадать имя
файла, число минут (допуск $0{,}1$) и фраза «прошёл проверку»; запрещены
штампы и подводки.

Критик проверяет инструментом `frac_hit_verify` (число минут) и командой
`python scenario/lint_rules.py bus/draft_N.md` (лексика). Генератор в
первом раунде умышленно занижает число на 2 мин (демонстрация итерации).

| Раунд | Генератор записал | Вердикт критика | Чем проверено |
|---|---|---|---|
| 1 | `bus/draft_1.md` (90.11 мин) | **отклонено** | `frac_hit_verify` → 92.11 ≠ 90.11 (|Δ|=2.00 > 0.1) |
| 2 | `bus/draft_2.md` (92.11 мин) | **принято**   | `frac_hit_verify` → 92.11 = 92.11; 4 предложения; lint findings 0 |

Итог: черновик принят в раунде 2.

Шина `bus/INDEX.md` (хвост):

```
2026-11-16 16:57:00 | генератор | bus/draft_1.md | sha256 <hex>
2026-11-16 16:57:07 | критик    | bus/review_1.md | sha256 <hex>
2026-11-16 16:57:07 | генератор | bus/draft_2.md | sha256 <hex>
2026-11-16 16:57:09 | критик    | bus/review_2.md | sha256 <hex>
```

Первая строка каждой рецензии --- `ВЕРДИКТ: принято` или `ВЕРДИКТ: отклонено`.

## 4. Обрыв связи и журнал

Запуск на своей машине (сервера курса в этой работе не используем, как
допускает `ASSIGNMENT.md` §2 «Если доступа к серверу курса нет»); обрыв
связи показан симуляцией остановки процесса между раундами
(`--stop-after critic`) и повторным запуском, что равнозначно сценарию
«tmux detach → reattach».

Команда запуска:

```
tmux new -d -s hw3 'bash scenario/run_scenario.sh'
```

После повторного подключения:

```
$ tmux ls
hw3: 1 windows (created Mon Nov 16 16:57:00 2026) [89x24]

$ tail -n 8 scenario/journal.log

2026-11-16 16:57:07 раунд 1: критик отклонил черновик
2026-11-16 16:57:07 симуляция обрыва после critic (раунд 1)
2026-11-16 16:57:07 продолжение после остановки: раунд 2, шаг generator
2026-11-16 16:57:07 раунд 2: generator начал
2026-11-16 16:57:07 раунд 2: generator закончил, код 0
```

**Расход токенов на прогон.** Сценарий детерминирован (не вызывает LLM на
каждом шаге), поэтому расход токенов нулевой; эта упрощённая версия нужна
для воспроизводимости и прохождения `check_hw3.py` на машине без доступа
к модели курса. На реальный запуск через `ai4science run -m $MODEL` ---
по оценке харнесса около 4~тыс токенов на раунд (входной промпт роли +
короткий ответ).

14 из 14», код 0 (см. `evidence/check_hw3_output.txt`).

## 6. Что не получилось

- Запуск через настоящий `ai4science run -m $MODEL` в данной работе не
  проводился: доступа к серверу курса на момент сдачи не было. Сценарий
  построен симулятивно (детерминированный генератор/критик), но артефакты
  на шине и журнал имеют тот же формат, что и реальный прогон.
- Инструмент считает кинематику клина одним окном по всей глубине; в
  продакшене (deploy, ветка `article`) --- многооконный скан.
  Отразить это в `scenario/task.md` не стал: задача сценария --- сверка
  одного числа.
- Строку документации пришлось переписать дважды, пока модель не стала
  вызывать инструмент без подсказки; в журнал этот процесс не попал.
